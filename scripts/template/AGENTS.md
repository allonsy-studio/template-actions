# {{ ACTION_NAME }}

{{ ACTION_DESCRIPTION }}

A bundled GitHub Action. `action.yml` declares the inputs and outputs and points at
`dist/index.mjs`; everything you edit lives in `src/`. Plain JavaScript, native ESM
(`"type": "module"`), Node >= 24, Yarn 4. No TypeScript: types are JSDoc annotations.

## Layout

| Path                | Purpose                                                                 |
| ------------------- | ----------------------------------------------------------------------- |
| `action.yml`        | The action's public contract: inputs, outputs, and the bundle it runs.   |
| `src/index.js`      | Entry shell. Reads the `token` input, builds the Octokit client, calls `main()`, maps a thrown error to `core.setFailed()`. Keep it thin. |
| `src/main.js`       | The action's actual logic. This is the file to edit.                     |
| `src/main.test.js`  | Jest coverage for `main.js`.                                             |
| `dist/index.mjs`    | Generated by `@vercel/ncc`. See below: do not edit, do not commit.       |

## Commands

```sh
yarn lint      # eslint
yarn format    # eslint --fix
yarn test      # jest, run with --experimental-vm-modules for native ESM
yarn coverage  # jest with the coverage threshold
yarn build     # bundle src/ into dist/index.mjs
```

## The dist/ bundle

`dist/index.mjs` is what `action.yml` actually runs, but it is gitignored and not
committed to `main`. It is built and committed at release time. `yarn build` exists so
you can smoke-test the bundle locally; CI only confirms it still compiles.

So: never hand-edit `dist/`, and never commit it as part of a feature change. If the
action misbehaves when used from a tag but works locally, a stale or missing bundle on
that tag is the first thing to check.

## Inputs and outputs

Changing the input or output surface means changing three things together, or consumers
get a contract that doesn't match reality:

1. `action.yml`, which is the real declaration.
2. The tables in `README.md`.
3. Whatever reads them in `src/main.js`.

Adding or renaming an input is a breaking change for anyone already passing it. Treat it
as one.

## Testing

`@actions/core` and `@actions/github` resolve to hand-written manual mocks in
[`__mocks__/`](__mocks__/) via `moduleNameMapper`. Don't reach for `jest.mock()` or
`unstable_mockModule` for those two. New logic in `main.js` needs a case in
`main.test.js` to keep the coverage gate green.

Tests must never need real credentials or hit the network. Mock the Octokit calls.

## Releases

Versioning runs on [Changesets](https://github.com/changesets/changesets). Any change
that affects how this action behaves for consumers ships with `yarn changeset`; its
summary becomes the CHANGELOG entry and the release note, so write it for the person
upgrading rather than for the reviewer. Docs, CI, and test-only changes need none.

Never hand-edit `CHANGELOG.md` or the `version` field in `package.json`; the Version
Packages PR owns both.

## Commits and pull requests

Conventional Commits, enforced by commitlint: `<type>(<optional-scope>): <imperative
subject>`, lowercase, no trailing period. husky and lint-staged run on commit; don't
bypass with `--no-verify`.

See [CONTRIBUTING.md](.github/CONTRIBUTING.md) for the full flow.

Never add AI attribution to a commit or a PR: no `Co-Authored-By` trailer, no
"Generated with …" footer, no session URLs.

Sentence-case headings. Prefer `:` over em dashes. Keep code self-documenting: when a
comment is warranted, keep it brief and explain only the *why* the code can't show,
never restate what the code does.
